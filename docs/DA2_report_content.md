**Project:** Satellite Imagery Knowledge Graph (GraphRAG for Earth Observation data)

## 1. Aim

Implement the DA1 design (15 relations, BCNF) as a working Oracle database, and demonstrate:
1. table creation with all integrity constraints
2. realistic sample records
3. SQL queries, from simple to advanced
4. PL/SQL programs: functions, a package, procedures, cursors, exception handling and triggers
5. transaction control, DDL changes and access control (DCL)

### 3.2 Design decisions in the DDL

| Decision | Reason |
|---|---|
| `GENERATED BY DEFAULT ON NULL AS IDENTITY (START WITH 10000)` | automatic surrogate keys for new rows; sample data uses IDs 1–9999, so they never clash |
| Natural keys kept as `UNIQUE` (satellite_name, basin_code, file_path, …) | preserves the candidate keys from normalization |
| Embeddings and attributes as `CLOB` + `CHECK (… IS JSON)` | Oracle XE has no vector type; the JSON check guarantees valid data |
| `TIMESTAMP DEFAULT SYSTIMESTAMP` | records when each row was created |
| Every FK column indexed (12 indexes) | faster joins, and avoids table locks when deleting a parent row |

### 3.3 Views

| View | Purpose |
|---|---|
| `v_image_summary` | image + sensor + satellite + location + basin in one row (a 5-table join reused by queries and the app) |
| `v_forest_change` | each lineage change with its location, basin, both images' cloud cover and both detections' confidence |

## 4. Constraints Implemented

| Type | Count | Examples |
|---|---|---|
| PRIMARY KEY | 15 | `pk_satellite`, `pk_detected_object` |
| FOREIGN KEY | 17 | `fk_obj_image` (CASCADE), `fk_loc_basin` (SET NULL), `fk_img_sensor` (restrict) |
| UNIQUE (candidate keys) | 17 | `uq_satellite_name`, `uq_sensor (satellite_id, sensor_name)`, `uq_si (image_id, index_name)`, `uq_alert_change` |
| NOT NULL | most columns | all FKs with total participation |
| CHECK: ranges | many | `cloud_cover 0–100`, `confidence 0–1`, `lat −90…90`, `area > 0`, `rank > 0` |
| CHECK: enumerations | 10 | orbit_type, sensor_type, region_type, change_type, severity, alert_status, user_role |
| CHECK: multi-column | several | bbox `min < max`; `min ≤ mean ≤ max` for spectral indices; `prev ≠ curr`; `resolved_at` only when RESOLVED |
| CHECK: format | 5 | `IS JSON` on embeddings, attributes and weights; email `LIKE '%_@_%._%'` |
| DEFAULT | several | `sat_status 'ACTIVE'`, `alert_status 'OPEN'`, timestamps |

**Referential actions:**
- `ON DELETE CASCADE`: the child has no meaning without its parent (sensor → satellite, object → image, index → image, change/evidence → object, alert → change).
- `ON DELETE SET NULL`: the link is optional (location → basin, query → user, alert → user).
- *No action (restrict)*: deleting a sensor that still has images is refused, so history is never lost silently.

## 6. PL/SQL Programs (`plsql.sql`)

**Result:** 3 functions, 1 package spec, 1 package body and 4 triggers compiled with **No errors**.

### 6.1 Stand-alone functions

| Function | What it does | Used in |
|---|---|---|
| `fn_haversine_km(lat1, lon1, lat2, lon2)` | great-circle distance in km (DETERMINISTIC) | "near a river" filter (Q10, app finder) |
| `fn_classify_change(pct)` | returns DEFORESTATION (≥10%), GRADUAL_LOSS (≥3%), STABLE, REGROWTH (≤−10%) | `compute_changes` |
| `fn_forest_loss_pct(location, from, to)` | % tree-area loss between the first and last image in a date window, using `KEEP (DENSE_RANK FIRST/LAST)` | basin report, app dashboard |

### 6.2 Package `pkg_eo` (encapsulates the project's business logic)

```sql
CREATE OR REPLACE PACKAGE pkg_eo AS
  e_no_evidence EXCEPTION;
  PRAGMA EXCEPTION_INIT(e_no_evidence, -20001);
  PROCEDURE compute_changes;
  PROCEDURE raise_alerts (p_min_loss NUMBER DEFAULT 10, p_min_conf NUMBER DEFAULT 0.7, p_max_cloud NUMBER DEFAULT 40);
  FUNCTION  fn_query_confidence (p_query_id NUMBER) RETURN NUMBER;
  PROCEDURE finalize_query (p_query_id NUMBER);
  PROCEDURE add_detection (p_image_id NUMBER, p_type_name VARCHAR2, p_model_id NUMBER, p_conf NUMBER,
                           p_lat NUMBER, p_lon NUMBER, p_area NUMBER, p_new_id OUT NUMBER);
  PROCEDURE basin_report (p_basin_code VARCHAR2);
END pkg_eo;
```

| Member | PL/SQL features used | What it does |
|---|---|---|
| `compute_changes` | **explicit cursor** with the analytic `LAG() OVER (PARTITION BY location ORDER BY time)`, cursor FOR loop, **MERGE** (upsert) | builds the **EVOLVED_FROM lineage**: links each tree patch to the previous patch at the same location and stores change %, days and rate per month |
| `raise_alerts` | default parameters, implicit cursor loop, `NOT EXISTS` | raises an alert only when loss ≥ 10% **and** both detections have confidence ≥ 0.7 **and** both images have ≤ 40% cloud (*trust-aware alerting*). Severity: ≥25% CRITICAL, ≥15% HIGH, else MEDIUM |
| `fn_query_confidence` | aggregate in `SELECT INTO`, `NULLIF` | **confidence propagation:** retrieval-weighted mean of (detection confidence × clear-sky fraction) over the question's evidence |
| `finalize_query` | `RAISE_APPLICATION_ERROR(-20001)`, `CASE` | stores the confidence and a generated answer sentence on QUERY_LOG |
| `add_detection` | **SAVEPOINT / ROLLBACK TO**, `RETURNING INTO`, OUT parameter, nested block with `NO_DATA_FOUND`, `DUP_VAL_ON_INDEX`, `VALUE_ERROR`, `OTHERS` | validated insert of a new detection |
| `basin_report` | **parameterised cursor** `c_loc(cp_code)`, BOOLEAN flag, `RPAD` | prints forest loss per location in a basin |

### 6.3 Triggers

| Trigger | Timing / level | Purpose |
|---|---|---|
| `trg_obj_audit` | AFTER INSERT/UPDATE/DELETE, **row-level** on DETECTED_OBJECT | writes old/new values to AUDIT_LOG, using `INSERTING`, `UPDATING`, `:OLD`, `:NEW` |
| `trg_img_validate` | BEFORE INSERT/UPDATE OF capture_time, row-level | rejects a capture time in the future (ORA-20010). A CHECK constraint cannot use SYSTIMESTAMP |
| `trg_alert_resolve` | BEFORE UPDATE OF alert_status, row-level | stamps `resolved_at` automatically when the status becomes RESOLVED, and clears it otherwise |
| `trg_change_validate` | BEFORE INSERT/UPDATE, row-level on OBJECT_CHANGE | both objects must be at the same location, and the previous one must be older (ORA-20030/20031) |
| `trg_alert_stmt_audit` *(extras.sql)* | AFTER INSERT/UPDATE/DELETE, **statement-level** on ALERT | one audit row per statement, however many rows changed |

> **Issue found during testing:** the first version of `trg_alert_stmt_audit` used `CASE WHEN INSERTING …` inside the SQL INSERT. `INSERTING` is a PL/SQL-only boolean, so the trigger compiled **invalid**. Later statements touching ALERT then failed with **ORA-04098** (even a DELETE on DETECTED_OBJECT, because it cascades to ALERT). **Fix:** evaluate `INSERTING`/`UPDATING` in PL/SQL `IF` statements into a variable, then insert the variable.

## 8. SQL Queries (`queries.sql`): purpose, concepts and actual results

| Q | Question answered | SQL concepts | Result |
|---|---|---|---|
| Q1 | first 10 images with satellite, sensor, location | view (5-table join), `FETCH FIRST` | 10 rows; all 10-Apr-26 images, e.g. image 1 Manaus, Sentinel-2B MSI, 31.4% cloud |
| Q2 | locations outside any basin | `LEFT JOIN … WHERE b.basin_id IS NULL` (anti-join) | 3 rows: Chennai Coast, Rotterdam Port, Dubai Marina |
| Q3 | clear-sky (< 20% cloud) images in Q3 2026 | timestamp range, `ORDER BY` | 12 rows; clearest is image 23, Tonle Sap, 3.7% |
| Q4 | images and average cloud per satellite | `JOIN`, `GROUP BY`, `COUNT`, `AVG` | 4 satellites × 15 images; avg cloud 26.5–32.5%. Sentinel-1A has no images, so the inner join drops it |
| Q5 | detections per object type, with > 5 detections | `GROUP BY … HAVING` | 7 types (Building 56, Tree 45, Water 40, Vessel 35, Road 25, Cropland 25, Bare Soil 20); Wildfire Scar removed by HAVING |
| Q6 | objects per river basin | 4-hop `LEFT JOIN` chain, aggregate | Godavari 45, Mekong 35, Amazon 33, Congo 30, Danube 20 |
| Q7 | images cloudier than average | **non-correlated subquery** | 8 rows, cloudiest image 18 (Mbandaka, 53.3%) |
| Q8 | latest tree area per location | **correlated subquery** (`MAX` per location) | 9 rows; Kisangani has the smallest remaining forest (2.61 km²) |
| Q9 | deforested locations with **no** alert | **MINUS** set operator | Manaus, Bhadrachalam: their evidence was too cloudy or uncertain, so no alert was raised |
| **Q10** | **"rapid deforestation near river basins in Q3"** | view + PL/SQL function in `WHERE`, multi-table join | **10 rows**: Manaus, Kisangani, Tonle Sap, Bhadrachalam; 38–174 km from the river; fastest rate 16.15%/month |
| Q11 | the same events ranked by trust | `LEAST`, `GREATEST`, arithmetic expression | best Kisangani 29-Sep (0.584), worst Manaus 27-Aug (0.306) |
| Q12 | cumulative loss and rank per period | **window functions** `SUM() OVER`, `RANK() OVER` | 36 rows; e.g. Kisangani cumulative 13.87% by 22-Jul |
| Q13 | full lineage chain of each forest patch | **hierarchical query** `CONNECT BY`, `SYS_CONNECT_BY_PATH`, `LEVEL` | 36 rows; e.g. `1 → 3 → 5 → 7 → 9` (Manaus) |
| Q14 | does NDVI agree with the tree area? | statistical aggregate `CORR` | 0.442 (positive). Moderate because each location starts with a different forest size |
| Q15 | vessels by class | **JSON functions** `JSON_VALUE … RETURNING NUMBER` | cargo 11 (avg 127.3 m), tanker 9 (160.7 m), passenger 8 (138.8 m), fishing 6 (101 m) |
| Q16 | images by resolution class | `CASE` inside `GROUP BY` | High (≤10 m) 30 images, Medium (≤30 m) 30 |
| Q17 | top-3 evidence per logged question | 6-table join | 12 rows; question 1's top evidence is Kisangani (0.9484) |
| Q18 | alerts dashboard | `LEFT JOIN`, `ORDER BY CASE` (custom sort) | 4 alerts; 10000 HIGH Kisangani RESOLVED (Aarav Menon), 10003 HIGH Tonle Sap, 10002/10001 MEDIUM Tonle Sap |
| Q19 | transaction demo | `SAVEPOINT`, `UPDATE`, `ROLLBACK TO` | "5 rows updated" → "Rollback complete"; data unchanged |
| Q20 | integrity demos | invalid DML | ORA-02290 (cloud 140), ORA-02291 (missing parent image), ORA-02292 (delete a satellite with child rows) |

**The key query (Q10):**
```sql
SELECT fc.location_name, fc.basin_name, fc.curr_time, fc.change_pct, fc.rate_pct_per_month,
       ROUND(fn_haversine_km(l.latitude, l.longitude, b.river_ref_lat, b.river_ref_lon)) AS km_to_river
FROM v_forest_change fc
JOIN location l    ON l.location_id = fc.location_id
JOIN river_basin b ON b.basin_id = l.basin_id
WHERE fc.change_type = 'DEFORESTATION'
  AND fc.curr_time >= TIMESTAMP '2026-07-01 00:00:00'
  AND fc.curr_time <  TIMESTAMP '2026-10-01 00:00:00'
  AND fn_haversine_km(l.latitude, l.longitude, b.river_ref_lat, b.river_ref_lon) <= 300
ORDER BY fc.rate_pct_per_month DESC;
```

## 12. Conclusion

The DA1 design was implemented as 15 constrained tables with 2 views and 12 indexes, loaded with 247 consistent sample detections. A PL/SQL layer (3 functions, a 6-member package, 5 triggers) implements the project's three ideas inside the database:
1. **temporal lineage** (`compute_changes`, Q13)
2. **trust-aware alerting** (`raise_alerts`, Q9/Q11)
3. **confidence propagation** (`fn_query_confidence`)

All outputs matched the independently predicted values. The 19 queries cover joins, aggregates, subqueries, set operators, window functions, hierarchical queries, JSON and transactions. Integrity violations are rejected with clear errors. The same database is extended with a Neo4j graph in DA3 and used by the web application in the final project.
